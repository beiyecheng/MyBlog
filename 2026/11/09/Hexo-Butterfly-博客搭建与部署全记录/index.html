从零搭建 Hexo + Butterfly 博客并部署到 GitHub Pages

发表于2026-11-10|更新于2026-11-10|技术教程
|总字数:3915|阅读时长:16 分钟|浏览量:

这篇记录的是我实际走一遍的完整流程，包括每一步为什么这么做、哪些地方会静默出错、以及上线后怎么验证。折腾过一次之后，最容易丢的不是配置，是「当时为什么这么配」的记忆。

最终结果

  • 站点：https://beiyecheng.github.io/MyBlog/
  • 源码仓库（私密）：MyBlog-source
  • 页面仓库（公开）：MyBlog，只放编译后的静态文件

环境：Windows + Git 2.55 + Node.js 22.23.2 + Hexo 8.1.2 + Butterfly 5.7.2。

一、为什么必须用两个仓库

这是整套方案里最重要的一条认知：

仓库 放什么 谁看
MyBlog-source md 文章、_config.yml、主题源码 只有自己，私密
MyBlog hexo g 生成的 HTML/CSS/JS 所有人，公开

hexo d 推送的是编译产物，它不包含你的 Markdown。如果只保留一个页面仓库，源码丢了就是彻底丢了——文章找不回来，配置也得重配。所以源码必须单独一个私密仓库，日常 git push 到那边。

二、初始化项目

初始化后的目录里有 source、scaffolds、_config.yml、package.json，这时候 hexo 命令就能用了。

三、装 Butterfly 主题

hexo-renderer-pug 和 hexo-renderer-stylus 是 Butterfly 的硬依赖，不装的话主题的 .pug 模板和 .styl 样式根本编译不出来，页面会是空壳。

坑一：clone 下来默认在 dev 分支

git clone 之后主题停在 dev，版本号看着挺新（5.7.2），但那是开发分支，不是发布版。先切回稳定的 master：

坑二：主题内嵌 .git 会让源码仓库漏掉主题

themes/butterfly/.git 存在时，父仓库 git add . 只记录一个 gitlink，主题的真实文件不会入库。恢复的时候 clone 下来是个空目录。

想让主题跟着源码一起备份，就把这个目录删掉：

代价是以后升级主题不能 git pull，得整目录覆盖——可以接受。

四、主题配置必须复制成根目录文件

之后所有主题相关设置都改 _config.butterfly.yml，不要直接改主题目录里的那份。这样以后升级主题覆盖 themes/butterfly 时，你的配置不会跟着被覆盖。

坑三：别拿旧版配置片段直接粘贴

网上流传的 Butterfly 模板大多是 4.x 写法，比如 code:、music:、danmaku: 这些键，5.x 已经改成了 code_blocks:、search.use: 等新结构。

危险的地方在于：粘进去不会报错。Hexo 会静默忽略不认识的键，页面照样生成，但新版默认项（侧栏卡片、搜索面板等）全丢了，你不回读生成的 HTML 根本发现不了。

正确做法是先复制完整配置，再逐项改值，让新旧键名对齐。

八、开启 GitHub Pages

静态文件推上去了不等于能访问。新仓库的 Pages 默认是关的，必须手动开一次：

  1. 打开仓库 Settings → Pages
  2. Source 选 Deploy from a branch
  3. Branch 选 main，目录选 /(root)
  4. 保存，等 1～2 分钟

没开之前访问是 404，这个 404 和路径配错的 404 长得一样，容易混。

九、日常流程

两条都要做。 只跑第一行，线上更新了但源码没备份；只跑第二行，源码在但页面没变。

十、上线验收清单

发布完别只看首页能打开，按下面几项过一遍，能提前发现大部分静默故障：

检查项 期望
首页 / 200，文章卡片数量对
归档、分类、标签、关于 都是 200
分类页（中文分类名要 URL 编码） 200，文章在列表里
css/index.css 200，两百 KB 左右
js/main.js 200
search.xml 200，条目数 = 文章数
atom.xml 200，订阅入口可用
sitemap.xml 200，可提交搜索引擎
随便一个不存在的路径 404
页面里裸根路径链接 0 处

几个容易让人误以为出问题、其实正常的现象：

  • css/var.css 是 0 字节：它是纯变量文件（$bright-blue 这些），不产出样式，变量已经并进 index.css，页面也不引用它。
  • 部署日志刷一堆 LF will be replaced by CRLF：Git 换行提示，不影响线上显示。
  • 刚发布打开还是旧样式：Pages 有 CDN 缓存，Ctrl+F5 强刷。

十一、补齐订阅、站点地图与字数统计

能跑起来之后，我先补的是三样「缺了不像博客」的东西：订阅、站点地图、字数统计。它们的共同点是不影响页面长相，但少一样就在别处吃亏。

三者分工不一样：

  • atom.xml：RSS 阅读器订阅入口，读者不用天天来刷站点
  • sitemap.xml：提交给 Google Search Console / Bing 站长工具，能明显加快收录
  • 字数统计：文章头显示「本文共 xxx 字，需要 x 分钟」，侧栏显示全站总字数

字数统计有个坑：主题里的开关只是显示开关，后端依赖 hexo-wordcount 插件。只开主题开关不装插件，页面上什么都不会出现，也不会报错——又是一个静默失败。

分类体系

建站时顺手建的分类只有一个，导航里「分类」点进去很单薄。后来把文章理成三类：

分类 放什么
技术教程 建站、部署、踩坑记录
书单 读书笔记
随笔 杂记、测试草稿

有个细节值得单独记一笔：导航里「书单」这一项链接指向 /categories/书单/，导航文字必须和真实分类名一致。如果只改导航不改分类，点进去页面标题写的是另一个词，会让人以为点错了。要改名就两处一起改。

十二、图床：GitHub 仓库 + jsDelivr + PicGo

图片不能塞进博客源码仓库——源码是私密的，图片链接要公开；塞进去还会让仓库越来越臃肿。所以单独开一个公开的图床仓库。

为什么选这套

对比过 Cloudflare R2：R2 给 10GB 存储、出网流量免费，稳定性和速度都更好，但开通时要绑支付方式（信用卡或 PayPal），没有卡就卡在第一步。个人博客访问量小，用 GitHub + jsDelivr 零门槛就够，真到图片打不开那天再迁 R2 不迟。

三步配好

1. 建一个公开仓库

比如 blog-img，创建时勾 Add a README，这样默认就有 main 分支。必须 Public，私密仓库 jsDelivr 取不到文件。

2. 生成细粒度 Token

GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens：

  • Repository access 选 Only select repositories，只勾 blog-img
  • Permissions 只给 Contents: Read and write
  • 有效期设 1 年

给最小权限的意义在于：这个 token 就算泄漏，也只能动图床仓库，碰不到源码仓库。

3. PicGo 填 5 个字段

装 PicGo 正式版，图床设置 → GitHub：

字段 值
设定仓库名 beiyecheng/blog-img
设定分支名 main
设定Token 上一步的 token
指定存储路径 img/
设定自定义域名 https://cdn.jsdelivr.net/gh/beiyecheng/blog-img@main

上传后自动得到这样的链接：

四个坑

  1. 仓库设成私密：PicGo 上传会成功，但 jsDelivr 打不开，返回 404。公开是硬条件。
  2. 忘了填自定义域名：PicGo 给的是 raw.githubusercontent.com 的地址，国内访问明显偏慢。
  3. 文件名带中文或空格：平时能显示，但哪天要换 CDN 前缀（比如换 raw 域名）时，转义和空格问题会一起爆出来。让 PicGo 用日期时间戳命名最省事。
  4. 公开仓库不是保险箱：传过的文件即使后来删掉，也能从提交历史里翻出来。身份证、后台截图、带密钥的界面截图一律不要传，这个仓库以后要传图片，就更要守住这条。

图片体积

单图压到 300KB 以内，GitHub 仓库总量控制在 1GB 以内。图片一多，jsDelivr 的加载会变慢，GitHub 也可能限流。截图优先存 WebP。

十三、评论系统：最后用了 Giscus

一开始我要的是 Waline——支持匿名评论、有管理后台，看起来最像「正经评论系统」。中途换成了 Giscus，原因值得单独写一节。

走过的一条弯路：Waline + Cloudflare Workers

Waline 官方支持的部署方式里没有 Cloudflare Workers（官方列表是 Vercel、阿里云、百度云、CloudBase、Deta、Railway、独立部署）。Workers 上只有一个社区实现 Waline_On_Worker（Hono + D1）。我还是按它走了一遍：

每一步都成功：拿到 https://waline.xxx.workers.dev，D1 五张表建好，JWT_SECRET 写入。然后：

workers.dev 这个域名在国内网络基本连不上，换长超时、换 HEAD/GET 都一样。这不是我配错了，是域名本身的问题——服务部署成功，和你自己能访问它，是两件完全不同的事。

要让它可用只有一条路：绑自己的域名（Workers 自定义域名必须是挂在 Cloudflare 账号下的域名）。我没买域名，所以这条线停在这里。Worker、D1、密钥全部保留，以后一条命令就能启用，不产生费用。

Giscus：把评论存进 GitHub Discussions

Giscus 的评论就是仓库里的 Discussions，不需要服务器、不需要数据库、不要钱。代价只有一条：读者必须用 GitHub 账号登录才能发言，没有匿名评论。技术博客可以接受这个代价。

GitHub 上做三件一次性的准备：

  1. MyBlog 仓库 → Settings → Features → 勾上 Discussions
  2. 装 giscus App：https://github.com/apps/giscus → 只授权 MyBlog
  3. 打开 https://giscus.app/zh-CN ，Repository 填 beiyecheng/MyBlog，Category 选 Announcements，Mapping 选 pathname，抄下生成的 data-repo-id 与 data-category-id

然后只改 _config.butterfly.yml 两处：

light_theme / dark_theme 是主题用来跟随站点明暗模式切换 iframe 主题的，不用再手写 preferred_color_scheme。

三个坑

  1. 评论区所在仓库必须公开。评论存进 Discussions，私密仓库的讨论区外人看不见，读者打开就是一片空白，而且页面不会报错。
  2. comments.count 和 lazyload 别乱开。主题的评论数统计依赖后端接口，Giscus 不提供；lazyload: true 也会让计数失效。这两个保持 false。
  3. 配完不会立刻生效。Pages 有 CDN 缓存，等 1～2 分钟，页面还得 Ctrl+F5 强刷。

十四、还能优化的地方

这套现在已经能正常跑了，但离「像个成品博客」还有距离：

该调的体验

  1. 首页版式：index_layout 现在是 3（左右交替），等有了封面图再决定要不要换成 4 或 5。
  2. 代码块：用的是 darker + mac 风格，如果你贴的多是长代码，可以把 height_limit 开起来，避免一屏全是滚动条。
  3. 图片灯箱与无刷新：lightbox: 现在是空值（等于关闭），填 fancybox 文章内图片就能点击放大；pjax.enable: true 则让站内跳转不再整页刷新。这两项都是改一行。

该工程化的

  1. GitHub Actions 自动部署：现在改完文章要在本地跑 hexo d。配一条 workflow，push 到源码仓库就自动构建并推到页面仓库，换台电脑也能写。
  2. 主题升级策略：.git 已删，升级就是覆盖 themes/butterfly，先确认 _config.butterfly.yml 还在根目录——它不在主题目录里，覆盖不会影响，但心里要有数。
  3. 刷一遍 SEO：description、keywords、每篇文章的 description 都补上，标题别用「无标题」。

小结

整套流程里最贵的四个教训：

  1. 源码和产物必须分开存，只备份其中一个等于没备份。
  2. 项目站点的 url 和 root 必须成对配，错了不报错，只会在线上静默 404。
  3. 旧版主题配置片段不能直接粘进新版，也不会报错，只会悄悄丢功能。
  4. 部署成功不等于可访问。一个服务部署完，第一件事是从你自己要用的网络实测一次，别拿日志里的「Successfully deployed」当验收结论。

Hexo 这类工具的通病就是「错得很安静」。所以每次改完配置，别只看命令有没有报错，要回读生成的东西。
